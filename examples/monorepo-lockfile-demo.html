01 — Overview

Monorepo 中的 Lockfile 挑战

单仓库中 lockfile 问题简单;monorepo 中多个包共享一个 lockfile,问题复杂得多。

my-monorepo/ ├── package.json ← workspaces 配置 ├── package-lock.json ← 所有 workspace 共享! ├── .npmrc ├── node_modules/ ← workspace 共享依赖 └── packages/ ├── pkg-a/ │ ├── package.json │ └── node_modules/ ← workspace 本地依赖 └── pkg-b/ ├── package.json └── node_modules/
⚠
核心矛盾: 构建脚本直接修改 node_modules 后,不会触发 package-lock.json 更新。下次 npm install 会把依赖恢复为 lockfile 中的版本,构建结果被覆盖。
场景 1
子包 package.json 变化
直接修改 packages/pkg-a/package.json 中的 dependencies
会更新根 lockfile
场景 2
构建脚本修改 node_modules
构建过程中替换 node_modules,但没改 package.json
不会更新 lockfile
场景 3
npm install --prefix
在子包目录执行 npm install,lockfile 可能不同步
条件更新 lockfile
场景 4
npm ci 在 CI 中失败
本地修改了 node_modules 未同步到 lockfile,CI 用 npm ci
npm ci 报错退出
02 — Structure

Lockfile 在 Monorepo 中的结构

npm workspaces 中所有 workspace 的包都记录在根目录 package-lock.json 的同一个 packages 字段下,key 使用路径前缀区分。

packages 字段 key 命名规则

Key 格式含义示例
""根项目根 package.json 的 name/version
node_modules/<pkg>根级别安装的共享包node_modules/lodash
packages/<pkg-name>workspace 包自身packages/pkg-a
packages/<pkg>/node_modules/<dep>workspace 私有依赖packages/pkg-a/node_modules/axios
node_modules/<pkg>/node_modules/<nested>嵌套依赖node_modules/express/node_modules/body-parser
Monorepo packages 结构JSON
"name": "my-monorepo", "lockfileVersion": 3, "packages": { // 根项目 "": { "name": "my-monorepo", "version": "1.0.0" }, // 根级别依赖 (所有 workspace 共享) "node_modules/lodash": { "version": "4.17.21", "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz", "integrity": "sha512-..." }, // workspace: pkg-a 自身 "packages/pkg-a": { "name": "pkg-a", "version": "1.0.0", "dependencies": { "lodash": "4.17.21" } }, // workspace: pkg-a 的私有依赖 "packages/pkg-a/node_modules/axios": { "version": "1.6.0", "resolved": "https://registry.npmjs.org/axios/-/axios-1.6.0.tgz", "integrity": "sha512-..." }, // workspace: pkg-b 自身 "packages/pkg-b": { "name": "pkg-b", "version": "1.0.0" } }

npm install 的更新流程

1
读取根 package.json 的 workspaces 配置
发现 packages/* 下的所有子包
↓
2
遍历所有 workspace,读取 package.json
解析每个包的 dependencies / devDependencies
↓
3
构建统一的依赖图 (dedupe)
在根 node_modules 扁平化共享依赖,workspace 内部依赖保留本地
↓
4
写入根 package-lock.json
所有 workspace 的依赖记录到同一个 lockfile,每个包路径作为 key 前缀
⚠
关键点: npm install 只检测 package.json 变化。如果只修改了 node_modules 而没改 package.json,lockfile 不会被更新,下次 install 会把依赖恢复为 lockfile 记录的版本。

04 — Commands

npm install vs npm ci 详细对比

在 monorepo 中,这两个命令的行为差异尤为重要。

npm install 执行流程Flow
npm install # 在 monorepo 根目录 Step 1: 读取根 package.json 中的 workspaces 配置 └─ 发现 packages/* 下的所有 workspace Step 2: 读取所有 workspace 的 package.json └─ 解析 dependencies / devDependencies Step 3: 读取根 package-lock.json (如果存在) └─ 作为当前状态的参考 Step 4: 比较 package.json 和 lockfile ├─ 如果 lockfile 满足 package.json 范围 → 直接使用,不变更 └─ 如果有新增/变化 → 重新计算并更新 lockfile Step 5: 安装依赖到 node_modules Step 6: 写入/更新 package-lock.json (如有变化)
npm ci 执行流程Flow
npm ci # 在 monorepo 根目录 Step 1: 读取根 package-lock.json └─ 必须存在,否则报错 Step 2: 删除根 node_modules 和所有 workspace 的 node_modules └─ 确保干净状态 Step 3: 根据 lockfile 精确安装每个包 └─ 版本、resolved URL、integrity 必须完全匹配 Step 4: 不读取 package.json 中的版本范围 └─ 完全按照 lockfile,不会更新 Step 5: 验证安装结果 └─ 校验 integrity 哈希
✓
推荐: 本地开发用 npm install,CI/CD 用 npm ci。monorepo 中两者都应在根目录执行。

npm workspaces lockfile 结构示例

npm workspaces 依赖结构Tree
# 扁平化结构: node_modules 下所有包在同一层级 my-monorepo/ ├── node_modules/ │ ├── lodash ← pkg-a 和 pkg-b 共享 │ ├── pkg-a → packages/pkg-a ← workspace 链接 │ └── pkg-b → packages/pkg-b ← workspace 链接 └── packages/ ├── pkg-a/ │ └── node_modules/ ← 仅私有依赖 │ └── axios └── pkg-b/ └── node_modules/ ← 仅私有依赖
pnpm 依赖结构 (非扁平化)Tree
# pnpm 使用 symlink,每个包有独立的 .pnpm 虚拟存储 my-monorepo/ ├── node_modules/ │ ├── .pnpm/ ← 真实包存储 (内容寻址) │ │ ├── lodash@4.17.21/ │ │ └── axios@1.6.0/ │ ├── lodash ← symlink 到 .pnpm/lodash@4.17.21 │ └── pkg-a ← symlink └── packages/ ├── pkg-a/ │ └── node_modules/ │ └── axios ← symlink 到根 .pnpm/axios@1.6.0 └── pkg-b/
→
pnpm 的优势: 内容寻址存储 (CAS) + symlink 模式,避免幽灵依赖 (phantom dependencies) 和扁平化依赖地狱,安装速度更快,磁盘利用率更高。
06 — Best Practices

最佳实践

不同场景下的推荐配置方案,确保 monorepo 的依赖锁定和构建确定性。

CI/CD使用 frozen-lockfile
CI/CD 环境中强制锁定,不更新 lockfile。使用 npm ci 替代 npm install。monorepo 中在根目录执行。
安全构建脚本不修改 node_modules
构建过程中不应直接操作 node_modules。如需修改依赖,应修改 package.json 后执行 npm install。
工具使用 workspace 命令
在根目录使用 npm install --workspace=pkg-a 或 npm run build --workspaces 确保 lockfile 同步更新。
版本锁定 npm 版本
在 package.json engines 字段或 .nvmrc 文件中指定 npm 和 node 版本,避免不同环境使用不同版本。
发布固定发布流程
发布前执行 npm install 确保 lockfile 最新,npm ci 验证构建,再执行 npm publish。
避坑统一 registry
团队使用相同的 npm registry。在 .npmrc 中配置 registry=https://registry.npmjs.org/,避免因镜像差异导致包内容不同。

CI/CD 配置示例

.github/workflows/ci.ymlYAML
# GitHub Actions CI 配置 name: CI on: [push, pull_request] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 # 锁定 npm 版本 (可选但推荐) - uses: actions/setup-node@v3 with: node-version: '20' cache: 'npm' # 缓存 node_modules # ✅ 正确: 使用 npm ci (monorepo 根目录) - run: npm ci # ✅ 正确: 构建所有 workspace - run: npm run build --workspaces # ✅ 正确: 测试所有 workspace - run: npm test --workspaces # ⚠️ 错误示例: 使用 npm install 而非 npm ci # - run: npm install # ❌ 可能更新 lockfile # ⚠️ 错误示例: 在构建脚本中修改 node_modules # - run: npm install lodash@latest # ❌ 不更新 lockfile,构建不一致
