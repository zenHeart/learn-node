01 — Structure

package-lock.json 数据结构

npm 9+ 使用的 lockfileVersion 3 格式,以扁平化的 packages 字段为核心。

顶层结构一览

package-lock.jsonJSON
{ "name": "my-app", // 项目名,必须与 package.json 一致 "version": "1.0.0", // 项目版本 "lockfileVersion": 3, // 格式版本 (npm 9+) "requires": true, // 兼容性字段,始终 true "packages": { // ⭐ 核心:扁平化的包索引 "": { // 空字符串 = 根项目自身 "name": "my-app", "version": "1.0.0", "engines": { "node": ">=18" }, "funding": { "url": "..." } }, "node_modules/lodash": { // key = 磁盘路径 "version": "4.17.21", // 精确版本 "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz", "integrity": "sha512-v2kDEe57...", // SHA512 完整性校验 "engines": { "node": ">=0.10.0" }, "dependencies": { "lodash": "4.17.21" } }, "node_modules/@babel/core": { "version": "7.23.9", "resolved": "https://registry.npmjs.org/@babel/core/-/core-7.23.9.tgz", "integrity": "sha512-...", "dependencies": { "@babel/code-frame": "^7.23.5", // 扁平引用,非嵌套树 "@babel/generator": "^7.23.6", "@babel/parser": "^7.23.9" } } }, "dependencies": { "lodash": { "version": "4.17.21", ... } } // 旧格式 v1/v2 兼容保留,新代码不再使用 }

关键字段解析

version 精确版本号
严格匹配 semver,格式为 主版本.次版本.补丁版本。^4.17.21 在 lockfile 中被解析为 4.17.21 这样的确切版本,不再保留范围语义。
resolved 下载地址
指向确切 tarball 的完整 URL,npm 直接从这个 URL 下载,绕过 registry 解析。不同 registry (官方 / 私有 / 镜像) 会产生不同的 resolved 值。
integrity 完整性校验
使用 Subresource Integrity (SRI) 格式:
sha512-[base64] (当前主流)
sha1-[hex] (旧格式)
sha256-[hex] (较少见)
dependencies 扁平引用
lockfileVersion 3 中,每个包的 dependencies 字段是扁平引用,仅表示"我的直接依赖是什么版本",不再把整个依赖树展开成嵌套结构。
optional 可选依赖标记
设为 true 时,该包安装失败不会导致整体安装失败。不同操作系统可能安装不同平台对应的可选包版本。
engines 引擎约束
声明运行该包所需的 Node.js 和 npm 版本范围。配合 npm config set engine-strict true 可强制校验,不匹配的包安装失败。
→
为什么 key 使用路径而非包名? npm 使用扁平化的 node_modules 结构,同一个包名只能有一个版本。路径 key 能清晰表示"哪个包依赖链中的哪个版本",解决嵌套依赖的歧义问题。

peerDependencies 冲突示例Scenario
package.json: { "dependencies": { "react-dom": "18.2.0", // 要求 react@^18 "antd": "5.12.0" // antd 5.x 要求 react@^18 } } // 安装时 npm 发现: react-dom@18.2.0 requires "react": "^18.0.0" ✅ 兼容 antd@5.12.0 requires "react": "^18.0.0" ✅ 兼容 // 结论: 可以共用 react@18.2.0 // ── 冲突场景 ── package.json: react-dom@17 + antd@5 (要求 react@^18) ERROR: 无法同时满足 peer dependency → 需要降级 antd 或升级 react-dom

为什么有 lockfile 仍可能版本不同 — 5 大原因

❌ 最常见手动改 node_modules
构建脚本中执行 npm install lodash@latest 后 node_modules 里是最新版,但 lockfile 仍是旧版。下次 npm install 会回退。
❌ Semver 范围 ^ 和 *
"axios": "^1.0" 允许 1.x.x 所有版本。如果删掉 lockfile 重装,可能装到 1.7.0 而非 1.0.0。
❌ npm 版本不同
npm 7/8/9 的依赖解析算法有差异。同一个 lockfile 在 npm 6 和 npm 9 下安装结果可能略有不同。
❌ Registry 差异
不同 registry 的 resolved URL 不同。私有的 npmmirror 可能缓存不同版本的包。
❌ optional 包平台差异
fsevents 仅 macOS,sharp 预编译二进制有平台差异。不同 CI 机器可能装到不同可选包。

05 — lockfileVersion

lockfileVersion 版本对照

三种 lockfileVersion 格式的结构差异和兼容性。

lockfileVersionnpm 版本核心结构兼容性
1npm 5, npm 6嵌套 dependencies 树npm 5-6 相互兼容
2npm 7, npm 8新增扁平 packages 字段npm 7+ 读 v2,v1 忽略新字段
3npm 9, npm 10packages 为主要结构npm 9+ 读 v3,v2/v1 降级提示

结构对比: v1 vs v2 vs v3

版本:

为什么 npm 9 要改变结构?

v1 问题嵌套结构体积膨胀
v1 的 dependencies 树把每个依赖的完整子树都展开。100 个包、深 5 层的依赖树,同一个包可能被声明几十次,lockfile 体积膨胀到数 MB。
v2 解决扁平化 packages 字段
packages 使用 path → metadata 的扁平映射,每个包只出现一次。lodash@4.17.21 在 lockfile 中只存一条记录,无论有多少包依赖它。
v3 完善完整支持 optionalDependencies
v3 在每个包的 packages 条目中支持 optional: true 标记,可选依赖的版本也完整锁定,解决了 v2 中可选依赖版本可能漂移的问题。
→
npm 6 打开 npm 9 生成的 lockfile: 会看到警告 "package-lock.json was generated with a newer version of npm",但通常仍能正常工作,因为旧版会忽略不认识的字段。
